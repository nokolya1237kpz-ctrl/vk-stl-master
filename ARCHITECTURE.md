# STL Master Architecture

## 1. Цель проекта

STL Master - веб-сервис для обработки больших STL-моделей, ориентированный на подготовку 3D-файлов к печати, хранению и передаче. Пользователь загружает STL-файл, запускает одну или несколько операций обработки, отслеживает прогресс задачи и скачивает готовый результат в ZIP-архиве.

Проект должен решать практические проблемы, которые часто возникают при работе с STL:

- файл слишком большой для удобной передачи или печати;
- сетка содержит ошибки: дырки, неориентированные нормали, самопересечения, невалидные треугольники;
- модель требует анализа перед печатью: габариты, количество треугольников, объем, площадь поверхности, замкнутость;
- модель нужно упростить без сильной потери формы;
- модель нужно разрезать на части, чтобы она помещалась в область печати;
- результат обработки должен быть доступен в виде набора файлов и отчета.

Ключевое требование: тяжелая обработка STL не должна выполняться внутри HTTP-запроса. Backend принимает запросы, валидирует входные данные и ставит задачи в очередь. Worker выполняет CPU- и memory-heavy операции отдельно, пишет прогресс и сохраняет результаты.

## 2. Основные пользовательские сценарии

### 2.1 Загрузка STL

1. Пользователь открывает веб-интерфейс.
2. Выбирает STL-файл или перетаскивает его в зону загрузки.
3. Frontend проверяет базовые ограничения: расширение, размер, пустой файл.
4. Backend принимает файл потоково, сохраняет его во временное хранилище и создает запись задачи.
5. API возвращает `jobId`, по которому frontend начинает получать статус обработки.

### 2.2 Анализ модели

1. Пользователь загружает STL и выбирает операцию анализа.
2. Worker определяет формат STL: binary или ASCII.
3. Worker считает метрики модели: количество вершин, количество треугольников, bounding box, примерный объем, площадь поверхности, наличие degenerate faces, замкнутость сетки.
4. Результат сохраняется как JSON-отчет и отображается во frontend.

### 2.3 Ремонт сетки

1. Пользователь запускает ремонт STL.
2. Worker выполняет операции нормализации сетки: удаление дубликатов, удаление вырожденных треугольников, попытка закрытия дыр, исправление ориентации нормалей.
3. После обработки worker сохраняет исправленный STL и отчет с перечнем примененных исправлений.
4. Пользователь скачивает результат в ZIP.

### 2.4 Уменьшение полигонов

1. Пользователь задает целевой процент уменьшения или целевое количество треугольников.
2. Worker строит внутреннее представление сетки и выполняет decimation/simplification.
3. Worker сохраняет упрощенную STL-модель и отчет: исходное количество треугольников, итоговое количество, коэффициент уменьшения, предупреждения о возможной потере качества.

### 2.5 Разрезание модели

1. Пользователь задает параметры разрезания: ось, количество частей или размер рабочей области принтера.
2. Worker вычисляет плоскости разреза и разделяет модель на части.
3. Каждая часть сохраняется отдельным STL-файлом.
4. Результаты упаковываются в ZIP вместе с отчетом.

### 2.6 Скачивание результата

1. Frontend показывает статус `completed`.
2. Пользователь нажимает кнопку скачивания.
3. Backend проверяет существование результата и срок его хранения.
4. API отдает ZIP-файл потоково, без загрузки всего архива в память.

## 3. Структура проекта

```text
vk-stl-master/
  backend/
  frontend/
  worker/
  docs/
  ARCHITECTURE.md
```

### 3.1 backend/

Backend отвечает за HTTP API, авторизацию при необходимости, загрузку файлов, постановку задач в очередь, выдачу статуса и скачивание результатов.

Планируемые зоны ответственности:

- REST API для загрузки STL;
- REST API для создания задач обработки;
- REST API для получения статуса и прогресса;
- REST API для скачивания ZIP результата;
- валидация входных параметров;
- потоковая запись загружаемых файлов на диск;
- запись метаданных задачи;
- интеграция с Redis queue;
- ограничение размера запросов и частоты обращений;
- очистка старых временных файлов.

Предполагаемая структура:

```text
backend/
  src/
    config/
    routes/
    controllers/
    services/
    queues/
    storage/
    validators/
    middleware/
  tests/
  package.json
```

### 3.2 frontend/

Frontend предоставляет пользовательский интерфейс для загрузки STL, настройки операций, просмотра прогресса и скачивания результатов.

Планируемые зоны ответственности:

- drag-and-drop загрузка STL;
- отображение параметров выбранного файла;
- форма выбора операции и параметров обработки;
- экран прогресса задачи;
- отображение результатов анализа;
- ссылки на скачивание результата;
- обработка ошибок API;
- запрет повторной отправки во время активной загрузки;
- адаптивный интерфейс для desktop и mobile.

Предполагаемая структура:

```text
frontend/
  src/
    app/
    components/
    features/
    api/
    styles/
  public/
  tests/
  package.json
```

### 3.3 worker/

Worker выполняет тяжелые операции над STL вне HTTP-процесса. Он читает задачи из Redis, обрабатывает файлы, пишет прогресс и сохраняет артефакты.

Планируемые зоны ответственности:

- чтение задач из очереди;
- загрузка исходного STL из локального или объектного хранилища;
- анализ геометрии;
- ремонт сетки;
- уменьшение числа полигонов;
- разрезание модели;
- упаковка результата в ZIP;
- запись прогресса в Redis/backend storage;
- обработка ошибок и retry policy;
- очистка временных файлов после завершения.

Предполагаемая структура:

```text
worker/
  src/
    jobs/
    stl/
    operations/
    progress/
    storage/
    utils/
  tests/
  package.json
```

### 3.4 docs/

Docs хранит проектную документацию, API-контракты, эксплуатационные инструкции и заметки по ограничениям.

Предполагаемая структура:

```text
docs/
  api.md
  deployment.md
  operations.md
  limits.md
  stl-processing.md
```

На текущем этапе эти файлы не создаются, чтобы не выходить за рамки задачи.

## 4. Архитектура обработки больших STL файлов

Большие STL-файлы нельзя обрабатывать как обычный JSON payload или держать целиком в памяти без необходимости. Основной принцип: HTTP-процесс принимает файл потоково, worker обрабатывает его отдельным процессом, а все промежуточные и итоговые файлы лежат во временном хранилище.

### 4.1 Поток загрузки

1. Frontend отправляет файл через `multipart/form-data`.
2. Backend использует streaming multipart parser.
3. Файл пишется на диск в каталог вида `storage/uploads/{jobId}/source.stl`.
4. Backend считает базовые параметры во время загрузки: размер, checksum, MIME/extension validation.
5. После успешной записи backend создает задачу в Redis.

Backend не должен читать файл полностью в Buffer. Максимум - небольшие chunks, которыми управляет stream pipeline.

### 4.2 Представление задачи

Минимальные данные задачи:

```json
{
  "jobId": "uuid",
  "operation": "analyze|repair|decimate|slice|pipeline",
  "sourcePath": "/storage/uploads/job/source.stl",
  "resultPath": "/storage/results/job/result.zip",
  "params": {},
  "status": "queued",
  "progress": 0,
  "createdAt": "ISO-8601"
}
```

### 4.3 Обработка в worker

Worker должен выполнять обработку поэтапно:

1. Проверить существование файла и лимиты размера.
2. Определить тип STL: binary или ASCII.
3. Провести быстрый preflight-анализ.
4. Выбрать стратегию обработки:
   - для небольших файлов допустима загрузка в память;
   - для больших файлов нужна chunk/stream стратегия там, где операция это позволяет;
   - для операций, требующих полной топологии сетки, нужен жесткий memory limit и отдельный процесс.
5. Записать промежуточный результат во временный каталог.
6. Сформировать ZIP и отчет.
7. Обновить статус задачи.

### 4.4 Изоляция тяжелых операций

Некоторые STL-операции могут потреблять много CPU и памяти. Для них нужно предусмотреть изоляцию:

- отдельный worker process;
- лимит одновременных задач;
- timeout на задачу;
- memory limit через настройки процесса/container/systemd;
- возможность завершить задачу при превышении лимитов;
- запись ошибок в job report.

Если библиотека обработки STL нестабильна или может падать на плохих файлах, ее лучше запускать в дочернем процессе. Тогда падение не убьет основной worker loop.

## 5. Очередь Redis

Redis используется как брокер задач и быстрое хранилище статуса выполнения.

Рекомендуемый вариант для Node.js - BullMQ поверх Redis. Он дает очереди, retries, delayed jobs, job events, concurrency и хранение прогресса.

### 5.1 Очереди

На MVP достаточно одной очереди:

```text
stl-processing
```

В будущем можно разделить очереди:

```text
stl-analysis
stl-repair
stl-decimation
stl-slicing
```

Разделение полезно, если операции имеют разные требования к CPU, памяти и времени выполнения.

### 5.2 Жизненный цикл задачи

Статусы задачи:

- `queued` - задача поставлена в очередь;
- `active` - worker начал выполнение;
- `processing` - идет обработка;
- `packing` - формируется ZIP;
- `completed` - результат готов;
- `failed` - задача завершилась ошибкой;
- `expired` - результат удален по TTL;
- `cancelled` - пользователь или система остановили задачу.

### 5.3 Retry policy

Ретраи должны быть осторожными. Ошибка из-за временной проблемы диска или Redis может быть повторена. Ошибка из-за невалидного STL не должна повторяться много раз.

Рекомендуемо:

- `attempts: 1` для ошибок валидации STL;
- `attempts: 2-3` для временных инфраструктурных ошибок;
- exponential backoff для повторов;
- фиксировать `failureReason` и технический stack trace отдельно от пользовательского сообщения.

## 6. API прогресса задачи

API должен отдавать прогресс без удержания тяжелого HTTP-запроса.

### 6.1 Polling MVP

Для MVP достаточно polling endpoint:

```http
GET /api/jobs/{jobId}
```

Пример ответа:

```json
{
  "jobId": "uuid",
  "status": "processing",
  "progress": 42,
  "stage": "repair_mesh",
  "message": "Repairing mesh topology",
  "resultUrl": null,
  "error": null
}
```

Frontend опрашивает endpoint каждые 1-2 секунды, пока задача не перейдет в `completed`, `failed`, `expired` или `cancelled`.

### 6.2 SSE после MVP

После MVP можно добавить Server-Sent Events:

```http
GET /api/jobs/{jobId}/events
```

SSE уменьшит задержку обновлений и количество лишних запросов. WebSocket на первом этапе не нужен, потому что прогресс однонаправленный: сервер сообщает frontend о состоянии задачи.

### 6.3 Источник прогресса

Worker обновляет прогресс в Redis:

```text
job:{jobId}:status
job:{jobId}:progress
job:{jobId}:stage
job:{jobId}:message
job:{jobId}:updatedAt
```

Backend читает эти значения и возвращает нормализованный ответ. Для завершенных задач backend также проверяет наличие ZIP-файла.

Важно: progress должен быть монотонным от 0 до 100. Если точное значение неизвестно, лучше обновлять stage и использовать приблизительные диапазоны.

## 7. Лимиты для стабильности сервера

Чтобы сервер не умер под большими STL или параллельными задачами, нужны жесткие лимиты.

### 7.1 Лимиты загрузки

- максимальный размер STL в MVP: 200 MB;
- запрет пустых файлов;
- разрешенные расширения: `.stl`;
- проверка сигнатуры binary STL и sanity-check ASCII STL;
- timeout на загрузку;
- rate limit на загрузку с одного IP;
- ограничение числа активных загрузок.

### 7.2 Лимиты обработки

- concurrency worker: 1-2 задачи на сервер для MVP;
- максимальное время задачи: 10-20 минут;
- максимальный размер распакованных/промежуточных файлов;
- максимальное количество треугольников после preflight;
- memory limit worker process;
- запрет бесконечных retry;
- остановка задачи при отсутствии прогресса дольше заданного времени.

### 7.3 Лимиты хранения

- TTL исходных файлов: 24 часа;
- TTL результатов: 24-72 часа;
- общий лимит storage directory;
- периодический cleanup job;
- запрет скачивания после удаления результата;
- атомарная запись ZIP: сначала temporary filename, затем rename.

### 7.4 Лимиты API

- rate limit на создание задач;
- rate limit на polling endpoint;
- максимальный размер JSON body для параметров операций;
- CORS только для разрешенных origin;
- request timeout;
- healthcheck endpoint без тяжелых проверок.

## 8. Операции MVP

### 8.1 Загрузка STL

MVP должен поддерживать загрузку одного STL-файла за задачу. Batch-upload можно оставить на будущие этапы.

Результат загрузки:

- `jobId`;
- исходное имя файла;
- размер файла;
- checksum;
- начальный статус задачи.

### 8.2 Анализ STL

Анализ должен возвращать:

- binary или ASCII STL;
- размер файла;
- количество треугольников;
- bounding box: width, height, depth;
- примерный объем;
- площадь поверхности;
- наличие вырожденных треугольников;
- примерная оценка замкнутости;
- предупреждения по качеству сетки.

### 8.3 Ремонт сетки

MVP-ремонт должен включать безопасные операции:

- удаление degenerate faces;
- объединение дублирующихся вершин по tolerance;
- исправление ориентации нормалей, если возможно;
- попытка закрытия простых дыр;
- отчет о том, что удалось и что не удалось исправить.

Не нужно обещать идеальный repair для любой модели. В UI и API должны быть предупреждения, что сложные self-intersections могут требовать ручной правки.

### 8.4 Уменьшение полигонов

MVP должен поддерживать параметры:

- target triangle count;
- или target reduction percent;
- preserve boundary по возможности;
- quality preset: conservative, balanced, aggressive.

Результат:

- новый STL;
- отчет по числу треугольников до/после;
- предупреждение о риске потери деталей.

### 8.5 Разрезание модели

MVP-разрезание:

- разрез по оси X/Y/Z;
- разрез на N частей;
- сохранение каждой части отдельным STL;
- отчет о размерах каждой части.

Более сложные сценарии, например автоматическая нарезка под конкретный принтер, можно вынести после MVP.

### 8.6 Скачивание ZIP результата

ZIP должен включать:

- обработанные STL-файлы;
- `report.json`;
- опционально `README.txt` с кратким описанием результата;
- логи обработки без внутренних секретов и stack trace.

Backend отдает ZIP через streaming response.

## 9. Технологии

### 9.1 Backend

Рекомендуемый стек:

- Node.js 20+;
- TypeScript;
- Fastify как HTTP framework;
- Multer или Busboy/Formidable для streaming upload, предпочтительно низкоуровневый stream parser;
- Zod для валидации входных параметров;
- BullMQ для очередей;
- Redis для очередей и статусов;
- Pino для логирования;
- Vitest или Jest для тестов.

Fastify предпочтителен из-за производительности, schema-based подхода и хорошей поддержки plugin architecture.

### 9.2 Frontend

Рекомендуемый стек:

- React;
- TypeScript;
- Vite;
- TanStack Query для запросов и polling;
- обычный CSS modules или Tailwind, если нужен быстрый UI;
- Vitest + Testing Library для unit/component tests;
- Playwright для e2e после появления основных сценариев.

### 9.3 Worker

Рекомендуемый стек:

- Node.js + TypeScript для orchestration;
- BullMQ Worker;
- отдельные child processes для тяжелых STL операций;
- библиотека для STL parsing/mesh operations;
- при необходимости Python CLI tools для зрелых geometry операций.

Практичный вариант: orchestration на Node.js, а сложные mesh-операции вынести в отдельный CLI-процесс. Это упростит контроль памяти, timeout и диагностику падений.

Возможные инструменты для geometry processing:

- meshoptimizer для decimation, если формат данных подходит;
- trimesh/Python для анализа и части repair/slicing операций;
- numpy-stl для простых STL операций;
- MeshLabServer/PyMeshLab как возможный backend для repair/decimation, если доступна установка и стабильная CLI-интеграция.

Выбор библиотеки нужно зафиксировать после короткого spike на реальных STL-файлах.

### 9.4 Storage and deployment

Для MVP на одном сервере:

- локальное файловое хранилище;
- Redis на том же сервере или managed Redis;
- systemd services для backend и worker;
- Nginx reverse proxy;
- HTTPS через Certbot;
- отдельные директории `uploads`, `work`, `results`, `logs` вне репозитория.

После MVP:

- S3-compatible storage для исходников и результатов;
- Docker Compose;
- отдельные worker nodes;
- metrics через Prometheus/Grafana или lightweight альтернативу.

## 10. План разработки по этапам

### Этап 0. Подготовка

- Зафиксировать требования MVP.
- Подобрать 5-10 тестовых STL разного размера и качества.
- Проверить библиотеки обработки STL на реальных файлах.
- Уточнить лимиты сервера: CPU, RAM, disk, swap.

### Этап 1. Каркас проекта

- Создать backend, frontend и worker приложения.
- Настроить TypeScript, lint, test runner.
- Поднять Redis локально и на сервере.
- Добавить базовые healthcheck endpoints.
- Настроить env-конфигурацию.

### Этап 2. Загрузка и очередь

- Реализовать streaming upload STL.
- Сохранять файл в storage directory.
- Создавать job metadata.
- Ставить задачу в BullMQ.
- Реализовать polling endpoint `GET /api/jobs/{jobId}`.

### Этап 3. Worker и анализ STL

- Реализовать worker loop.
- Добавить preflight-анализ STL.
- Считать базовые метрики.
- Записывать progress/stage/message.
- Сохранять `report.json`.

### Этап 4. ZIP результат

- Генерировать ZIP с отчетом.
- Реализовать endpoint скачивания.
- Добавить TTL и cleanup старых файлов.
