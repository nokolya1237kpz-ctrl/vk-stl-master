# STL Master Design System

Статус: foundation-only. Этот документ не подключается к приложению и не меняет текущий внешний вид.

## Назначение

Дизайн-система STL Master должна быть опорой для будущего восстановления интерфейса без риска для бизнес-логики. Она описывает язык продукта, токены, принципы и порядок миграции, но не требует немедленного изменения существующих компонентов.

Главный принцип: сначала сохраняем работоспособность, затем постепенно выравниваем визуальный слой. Любая будущая правка должна быть проверяема скриншотами, сборкой и отсутствием изменений в API/processing/admin logic.

## Философия

STL Master — профессиональный инженерный SaaS для подготовки моделей к 3D-печати. Визуальный стиль должен ощущаться как рабочий CAD-инструмент: точный, спокойный, технологичный и премиальный.

Ассоциации:

- CAD and mesh engineering;
- industrial design;
- precision tooling;
- AI-assisted repair;
- professional manufacturing workflow;
- controlled technical surfaces;
- reliable browser-based tooling.

Анти-ассоциации:

- не игровой интерфейс;
- не крипто/Web3;
- не яркий неоновый клубный стиль;
- не дешёвый Bootstrap;
- не копия Apple, Vercel, Linear или любого чужого продукта.

STL Master должен иметь собственный характер: тёмная инженерная среда, чистая типографика, аккуратные CAD-акценты, ощущение глубины через слои и материалы, а не через агрессивные эффекты.

## Визуальный тон

Интерфейс должен быть тёмным, но не пустым чёрным. Основа — глубокий navy/graphite, поверхности — спокойные иерархические слои, акцент — холодный cyan/blue для действия, выделения и технологических элементов.

Свечение допустимо только как инженерный акцент: граница активной панели, выбранный инструмент, section plane, focus state. Glow не должен окрашивать всё содержимое и не должен заменять композицию.

## Продуктовые правила

1. Функциональность важнее декоративности.
2. Визуальная премиальность достигается пропорциями, типографикой, сеткой и материалами.
3. Любой CTA должен быть очевидным, но не кричащим.
4. Viewer и Studio — рабочие области, они не должны выглядеть как лендинговая иллюстрация.
5. Landing продаёт реальные возможности, но не обещает функций, которых нет в коде.
6. Admin — утилитарный интерфейс управления, его дизайн должен быть плотным, ясным и русскоязычным.
7. Premium UI не должен менять логику доступа и заявок.

## Области интерфейса

### Landing

Landing должен показывать ценность продукта: загрузка модели, анализ, ремонт, разрез, соединения, проверка и экспорт. Визуальный слой может быть выразительным, но компоненты должны оставаться настоящей React/CSS-вёрсткой, а не скриншотами.

### Studio

Studio — центр продукта. Здесь важны плотность, стабильность, точные состояния и предсказуемые controls. Панели, toolbar, sidebar, inspector и viewport должны ощущаться как части одного инженерного инструмента.

### Admin

Admin должен быть рабочим русскоязычным интерфейсом. Приоритеты: безопасность операций, ясные статусы, таблицы без визуального шума, подтверждения для опасных действий.

### Premium

Premium — бизнес-слой поверх продукта. Он должен быть понятным и спокойным: цена, условия, действия и состояние пользователя. Визуальные улучшения не должны менять state machine.

## Ограничения текущего этапа

На этом этапе запрещено подключать новые CSS, менять imports, менять React, менять существующие стили и DOM. Все файлы в `frontend/src/design/` являются документацией и будущим фундаментом.
