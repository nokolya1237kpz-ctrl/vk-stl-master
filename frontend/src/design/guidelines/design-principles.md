# Design Principles

Статус: документация. Не подключено к приложению.

## Карточки

Карточка в STL Master — контейнер для конкретного решения или состояния, а не декоративная плитка. Она должна иметь тёмную инженерную поверхность, тонкую границу, ясный заголовок и минимум визуального шума.

Правила:

- радиус умеренный: 8-18px в зависимости от масштаба;
- граница должна помогать отделить слой, а не светиться без причины;
- hover допустим только для интерактивных карточек;
- изображение внутри карточки не должно иметь случайных белых краёв, рамок или растяжения;
- карточки одного ряда должны иметь согласованные высоты.

## Кнопки

Кнопка — действие. Основная кнопка использует cyan/blue/violet градиент только там, где это действительно primary action. Вторичные кнопки остаются тёмными с border.

Правила:

- текст и иконка не должны выходить за рамки;
- hit area не меньше 40px по высоте;
- loading/success/error состояния обязаны сохранять размер кнопки;
- destructive action не должен использовать primary blue style.

## Формы

Формы должны быть спокойными и проверяемыми. Ошибка объясняет причину и путь исправления. Поле не должно менять ширину при ошибке.

Правила:

- label всегда связан с полем;
- helper text вторичен по цвету;
- validation states не должны ломать layout;
- sensitive/admin actions требуют подтверждения.

## Таблицы

Таблица — главный паттерн Admin. Она должна быть плотной, читаемой и безопасной для массовых операций.

Правила:

- sticky action bar для bulk mode;
- русские статусы без смешения языков;
- опасные действия визуально отделены;
- long text truncation должен быть предсказуемым;
- строка не должна менять высоту при hover.

## Viewer

Viewer — рабочее пространство модели. Его визуал должен подчиняться модели, а не UI-эффектам.

Правила:

- модель всегда главный объект;
- сетка и gizmo вторичны;
- section plane тонкая, CAD-like;
- HUD не перекрывает важные части модели;
- cyan используется как акцент, не как глобальная заливка.

## Sidebar

Sidebar организует инструменты. Он должен быть плотным, сканируемым, с очевидным active state.

Правила:

- один активный инструмент;
- иконка и текст выровнены;
- disabled states читаются;
- длинные подписи не ломают ширину.

## Панели

Панели Studio и Admin показывают состояние и параметры. Они должны иметь ясную иерархию: title, metadata, controls, result.

Правила:

- одинаковая внутренняя сетка;
- border и elevation показывают уровень слоя;
- не вкладывать декоративные cards в cards без необходимости;
- controls группируются по смыслу.

## Диалоги

Диалог — временный слой для решения задачи. Он не должен выглядеть как отдельный landing page.

Правила:

- один главный action;
- close всегда доступен;
- error state сохраняет контекст;
- success state показывает следующий шаг;
- modal flow не меняет бизнес-логику доступа.

## Landing

Landing должен объяснять продукт через реальные возможности. Визуалы допустимы, но итоговая реализация должна оставаться настоящими компонентами.

Правила:

- first screen продаёт продукт и показывает Studio;
- workflow объясняет последовательность;
- connectors показывают реальные типы соединений;
- compare показывает измеримый результат;
- footer содержит полноценные контакты и структуру.

## Studio

Studio — основное приложение, здесь нельзя жертвовать функциональностью ради визуального эффекта.

Правила:

- не менять upload, job processing, API calls, viewer state ради визуала;
- визуальные правки делать scoped CSS;
- каждую правку проверять на пустом состоянии, активной модели и history;
- mobile/tablet должны сохранять доступ к основным действиям.

## Admin

Admin — зона контроля и безопасности.

Правила:

- всё на русском;
- destructive actions требуют подтверждения;
- bulk mode должен быть явно виден;
- таблицы и статусы важнее декоративных эффектов;
- визуальные изменения не должны менять права, удаление, quarantine, premium codes или jobs.
